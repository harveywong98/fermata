# AI 评测如何分解：范围、标准与判分方法

日期：2026-11-06

本地工具：Compose 按 `eval` / `tracing` profile 分别提供 [promptfoo](http://localhost:15500) 与 [Langfuse](http://localhost:13000)，启动见 [项目 README](../README.md)。当前尚未配置项目评测用例或 Agent 轨迹上报。

设计评测时，先把“测什么”“怎么跑”“怎么评分”分开。它们是独立的问题，不是一棵从简单到复杂的分类树。

## 1. 先看三个维度

| 维度 | 要回答的问题 | 可选方式 |
| --- | --- | --- |
| ① 评测范围 | 这次运行哪一段系统？ | 单节点、子链路、完整任务 |
| ② 成功标准 | 什么表现才算好？ | 结果正确、过程符合要求、性能成本达标 |
| ③ 判分方法 | 用什么证据判断达标？ | 代码规则、模型评审、人工评审 |

**一条评测，就是在这三个维度上分别作选择。** 不需要先判断它属于某种复杂的“评测类型”。一条案例也可以同时检查多个成功标准，使用不同判分方法。

## 2. 用同一个业务拆解

用户任务：**分析一条风险，判断属实还是误报，并更新状态。**

第一步不是选工具或指标，而是确定：**这次到底想知道什么？**

### 问题 A：新 Prompt 的判断能力有没有提高？

- **范围**：只跑 AI 判断节点，固定上游数据。
- **标准**：结论正确，分析依据没有编造；证据不足时保留判断。
- **方法**：代码比对人工核验的结论标签；依据部分用人工或校准后的模型评审。

```text
固定的请求、响应和风险规则
             ↓
         AI 判断节点
             ↓
     检查结论与分析依据
```

这测的是“给定这些信息，AI 能否正确判断”，不能证明上游 SQL 查询正确或下游更新成功。

### 问题 B：工作流上线后能不能完成任务？

- **范围**：SQL 查询 → AI 判断 → 状态更新，整条运行。
- **标准**：取对记录，判断正确，更新正确对象，并遵守必要的操作约束。
- **方法**：核对查询结果、结论标签、执行轨迹和最终数据库状态。

```text
测试环境中的初始数据
             ↓
          SQL 查询
             ↓
         AI 判断节点
             ↓
          状态更新
             ↓
  检查最终状态及必要过程约束
```

不能只看 Agent 是否回答“已更新成功”，还要验证实际状态。测试环境应能够重置，避免上一轮操作影响下一轮结果。

**同一个业务，因为想回答的问题不同，评测范围就不同。**

## 3. 其他概念分别放在哪里？

| 概念 | 它影响什么 |
| --- | --- |
| 开放问题／具体判断问题 | 主要影响成功标准和判分方法，不决定是否整条运行 |
| Agent／Workflow／RAG | 是被测系统是什么，三者都可以测局部或整体 |
| 多模型／多 Prompt | 是比较哪些版本，不是新的评测层次 |
| 正常数据／错误数据 | 是在什么条件下测试 |
| 错误传导 | 是一个专项问题：上游出错后，后续会怎样 |
| 线上／离线 | 是在哪里、用什么流量执行评测 |

### 开放问题不等于没有标准

例如“写一份风险分析报告”允许不同表达和方案，但其中的事实、证据引用、要求覆盖和操作建议仍然可以检查。

“判断风险是否属实”看似具体，但证据不足时，正确行为可能是“待复核”，不能为了方便评分而强行指定属实或误报。

**开放，不等于没有标准；具体，也不等于只能用代码判。**

### 离线评测不等于只检查静态答案

离线可以使用固定测试集，实际运行 SQL、检索、模型和工具。也可以只回放保存好的节点输入。执行哪一种，取决于评测范围。

## 4. 什么时候测错误传导？

不要把错误传导当成每次必做的一层。只有明确要回答下面的问题，才专门设计测试：

> 上游取错、漏掉或误解信息时，下游能否识别，系统会不会错误处置？

适合重点检查的情况包括：线上出现过相关失败；多个节点依赖上游语义判断；错误会触发高代价操作；产品设计中包含复核、纠错或恢复能力。

可以分别组织三组案例：

| 案例组 | 数据条件 | 验证目标 |
| --- | --- | --- |
| 单节点能力组 | 人工核验的固定输入 | 给定正确证据，节点能否判断正确 |
| 真实链路组 | 上游实际执行产生的输入 | 系统运行时能否完成任务 |
| 鲁棒性组 | 有现实依据的缺失、冲突或错配数据 | 系统是否识别异常、停止、转人工或恢复 |

需要注意：

- 比较单节点能力时，应保持输入一致，避免把上游差异混进模型能力差异。
- 下游没有原始证据，也没有核验工具时，不能当然要求它发现所有上游错误。
- 故障注入样本应单独统计，不能把它的失败率解释为正常流量下的错误率。
- 上游导致后续失败，不代表每个后续节点都应重复承担同样的错误责任。
- 正确恢复不一定是自动修复并完成；停止或转人工也可能符合业务要求。

## 5. 每次评测先填四句话

```text
我想验证：________________
因此运行：哪个节点／哪段链路／完整任务
通过条件：________________
判断依据：标签／证据／执行轨迹／最终状态，由谁判
```

例子：

```text
我想验证：修改风险判断 Prompt 后，是否减少误报且没有增加漏报。
因此运行：单个风险判断节点，两个版本使用同一批固定上游数据。
通过条件：分别比较属实、误报和待复核案例的结论表现，检查关键退步案例。
判断依据：人工核验标签由代码比对；解释中的证据支持情况由人工抽检。
```

填完后，再确定数据集、模型、Prompt、知识库和评分规则版本，以及重复次数、预算和运行环境。版本信息是让比较可解释的条件，不必与前面的三个维度混成一套分类。

## 6. 与当前仓库及评测 JD 的关系

当前讨论的 `prompt-is-all-you-need` 仓库，工作流评测主要采用：

> **单 AI 节点 + 业务正确性 + 代码规则判分。**

上游输入来自案例 YAML 或引用的 JSON fixture，并不在评测时实际执行整个工作流。工作流中的多个节点分别出题，再按模型、工作流、节点汇总结果。

这是一种有效的评测组合，但节点通过率不能直接当作整个任务的成功率。

所讨论 JD 的分层评测、轨迹评测、归因和发布门禁要求，意味着平台还要支持其他组合，例如完整任务加最终状态验证、开放分析加模型与人工评审。**JD 没有规定每次变更都必须全量运行，也没有规定每次都必须做错误注入。** 具体范围应依据验证目标、变更影响和业务风险决定。

## 7. 相关资料与边界

本文的三维框架是面向当前业务的整理方法，不是某一框架规定的唯一分类。以下一手资料支持其中的分层评测、混合判分与结果验证原则：

- [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)：组合使用代码、模型和人工评审，区分执行轨迹与最终环境状态。
- [LangChain：Evaluating AI Agents at the Run, Trace, and Thread Level](https://www.langchain.com/resources/agent-evals)：区分单步、完整执行和多轮会话评测。
- [τ-bench：Task Schema and Evaluation](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)：通过目标环境状态等条件评分，不默认要求唯一执行路径。

**先写清“想验证什么”，再选范围、标准和判分方法。**
