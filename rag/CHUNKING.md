# 文档切块与跨块语义处理

本文记录完整设计方向。当前已实现Docling结构解析、token预算、标题/表头补充、正文重叠和parent_id回读父单元；尚未实现OCR、规则语义推断、跨章节引用和自动上下文预算。实际边界见 [README.md](README.md)。Docling结构块不直接等于检索Chunk。

解析实现在 `documents/parsing.py`，切分实现在 `documents/chunking.py`；两者与向量调用分开。切分预算和向量输入校验共用 `embedding/tokenizer.py`，保证使用同一模型的计数规则。

## 按文档类型选择切法

先按文件类型解析，再按内容结构切。分页不等于语义边界，字符数也不等于模型token数。

|文档类型|常见内容|推荐切法|防止切断的重点|
|---|---|---|---|
|Word：制度、分类标准|章节、条款、定义、例外|按标题层级和完整条款切；超长条款拆成关联子块|条件、结论、例外尽量一起保留；每块带标题路径|
|Word：操作手册|操作目标、步骤、注意事项|一个操作目标作为父单元，步骤组作为子块|保留前置条件和步骤顺序，警告与对应步骤关联|
|Word：案例报告|背景、现象、分析、结论|一个案例作为父单元，按分析环节拆子块|每块带案例标识；命中后补读相关依据和结论|
|PDF：文本型规范|跨页条款、多栏正文、页眉页脚|恢复阅读顺序、去除重复页眉页脚后，按章节和条款切|不要直接一页一块；合并跨页段落，识别跨页表格|
|PDF：扫描件|图片中的正文和表格|OCR与版面识别后，再按正文和表格结构切|先检查漏字、错序、漏行；切块无法修复解析错误|
|PDF：图文说明|图、图注、说明文字|图片与图注、相关段落关联成一个单元|保留图号和引用；纯文本向量不能表达全部图形信息|
|Excel：分类目录|类别、编码、级别、说明|一个类型一块；列多时拆子块并重复类型标识|表头、合并单元格的上级类别补到每块，保留原始坐标|
|Excel：规则表|条件、动作、例外、优先级|一条完整规则一块；跨多行的规则合并|不把条件列和结论列拆开，保留单位与脚注|
|Excel：统计明细|大量记录、数值、汇总|通常放结构化表供SQL查询；说明和口径可向量化|不靠向量检索保证统计完整性，保留主键与统计口径|
|Markdown／HTML／飞书文档|标题、列表、代码块、表格|按标题和结构块切，必要时组合相关小块|尽量保持代码块、列表项和表格行完整；原始block不一定就是检索Chunk|
|TXT：类型列表、术语表|一行一个名称或定义|一个类型及其说明一块|不为了凑长度，把不同类型混成一块|
|TXT：连续正文|缺少明确结构的段落|先按段落，再按句子切，必要时少量重叠|不从句子中间机械截断，保留近距离指代上下文|

如果完整表格行、代码块或句子本身超过硬上限，也必须继续拆分，保留共同的语义单元标识和原文位置，不能直接截断丢弃尾部。

## 第一版长度预算

以当前选择的BGE-base-zh-v1.5为基准：完整输入上限512 tokens，正文目标约350 tokens，必要时对连续正文保留约40～60 tokens重叠。以上是初始参数，尚未经过本项目长文档检索评测。

- 用模型自身tokenizer计算最终输入长度，包含标题、表头、重叠文本和特殊token。
- 长度不是必须凑满的目标。一个完整类型定义只有几十tokens，也独立保留。
- 先保持语义完整，再处理超限。背景过长时只保留定位所需的标题与标识。
- 超限时继续按句子、步骤或子条件拆分；最后不得不按token硬切时，标记`split_reason`并保留原文关联，禁止静默截断。
- 重叠仅用于有连续语义的正文。两个独立类型、两条独立规则之间不默认重叠。

```text
content：当前块正文

embedding_text：
标题路径：电力数据分类 / 用户信息 / 身份标识
当前块正文……
```

`embedding_text`改变时必须重新计算input_hash和向量，即使content没有改变。必要背景应来自文档结构或已核验资料，第一版不让大模型自由补写定义。

## 不同跨块问题的处理

|问题|优先处理方式|边界|
|---|---|---|
|切分边界打断相邻句子的条件或解释|按句子切，必要时增加少量overlap|重叠只覆盖局部，不能保证完整规则都在范围内|
|不知道该块属于什么主题|向量化时附带标题路径、类别、表头|背景占用输入预算，不能无限重复|
|一条规则太长，条件与例外位于不同块|小块召回，关联同一语义单元后补读|父单元过大时仍需按预算选择证据，不能无上限拼接|
|“该字段”“上述情况”指代前文|补读同单元内相邻块|相邻不等于相关，跨主题时不自动扩展|
|引用其他章节或附录|保存显式引用，命中后定位被引用内容|ordinal前后相邻关系解决不了远距离引用|
|多个重叠块都被召回|按语义单元聚合，对重复来源范围去重|不能删除不同来源仅正文相同的块|

父子块的“父”是规则或小节这一逻辑单元，不要求生成向量。当前在document_chunk中用chunk_role=parent保存父正文，子块以parent_id自关联，不需要拼接带重叠的子块恢复原文。下方semantic_unit_id是早期分组示例，运行时以显式parent_id为准。

语义切块（用句组向量变化判断边界）和模型辅助切块留作后续方案：前者需要额外编码和阈值调试，后者有成本和生成错误风险；都不自动保证条件与例外完整。

## 与现有DDL的对应关系

见 [storage/sql/schema.sql](storage/sql/schema.sql) 和 [存储约定](storage/sql/README.md)。

|字段|用途|
|---|---|
|document_id|确定来源文档|
|chunk_set_id|确定解析、切块批次；检索与补读必须使用同一生效批次|
|ordinal|块在本批次中的顺序，用于预览和邻居读取；不是文档页码|
|content|本块正文|
|embedding_text|真正参与编码的正文与必要背景|
|content_hash / input_hash|分别检测正文和实际编码输入变化|
|metadata|标题路径、语义单元、页码、表格位置、切分原因及显式引用等可变结构|

```json
{
  "heading_path": ["电力数据分类", "用户信息", "身份标识"],
  "semantic_unit_id": "section-3-rule-2",
  "block_type": "paragraph",
  "page_numbers": [12, 13],
  "split_reason": "token_limit"
}
```

semantic_unit_id由解析和切块过程生成，在`document_id + chunk_set_id`范围内解释；相邻页的同一规则可共用一个标识，不把不同批次的相同编号关联起来。Excel来源位置可记录sheet_name、row_start、row_end等。需要引用定位时保留解析器的原始元素标识，具体字段由解析适配器统一。

## 检索后的处理顺序

1. 限定知识库、生效批次和embedding_profile，召回相关小块。
2. 按文档、批次及语义单元聚合，合并重复来源片段。
3. 如果命中只是规则的一部分，优先补读同单元的条件、例外和示例；必要时读取同小节的邻居。
4. 处理可定位的显式引用，限制扩展范围与次数，避免循环引用和无界读取。
5. 在Agent输入预算内整理证据，保留文档ID、Chunk ID和来源位置。未能补齐重要条件时明确标记，不能把片段包装成完整依据。

例如命中“设备编号排除条件”，补读同规则的“身份证识别条件”和正反例；不会默认把下一章节的无关内容全部追加。

## 如何验证策略

已有 [电力类型Embedding测试](../docs/research/embedding-benchmark/REPORT.md) 使用短类型定义，不能证明长文档切块参数最优。

- 固定同一批真实文档和业务问题，比较最终输入约250、350、450 tokens三档预算；每档都受512硬上限约束。
- 再分别比较不重叠、少量重叠和命中后扩展，不同时改变所有参数。
- 标准答案关联原文证据位置或稳定的源元素，不固定某一切块方案生成的Chunk ID。
- 分开观察召回相关证据、条件与例外完整性、重复内容比例、无关上下文量和编码耗时。
- 跨块需要多段依据的题，只有全部必要证据被保留才算证据完整；命中其中一段不算完整解决。
- 模型无法编码或解析丢失的内容另行统计，不能归因于切块策略。
